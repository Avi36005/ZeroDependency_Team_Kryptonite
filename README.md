# depx

**Dependency x-ray.** Point it at a repository and it tells you the truth about
what your code actually depends on — which is rarely what the manifest claims.

Ten languages. Fully offline. Zero third-party dependencies.


That is the whole output, unedited. Exit code 1 when ghosts or broken imports
are found, so it works as a CI gate.

Captured output for every command and every interesting case is in
[snips/](snips/) — including [a repo that fakes an empty
manifest](snips/08-zero-dep-vendored.txt) and [a normal-looking app with four
different problems](snips/12-realistic-app.txt). All of it is generated by
`make snips`, so it cannot drift from what the tool actually prints.

## Why

Models invent dependencies. A 2025 USENIX Security study of 576,000 generated
code samples found that **19.7% of the packages the models recommended did not
exist** — and the invented names repeat, so attackers can pre-register them and
wait. It is a supply-chain attack in which the victim never makes a typo. As
the share of AI-written code grows, so does the window.

`depx ghosts` finds those imports — while the name is still unclaimed, if you
check it against the registry in time.

One thing depx will not do is claim more than it can show. It proves an import
resolves to **nothing in your project**; proving a name exists nowhere would
need a shipped copy of the registry index, which is exactly the kind of
dependency this tool refuses to have. So the finding says the build breaks
here, and leaves the registry lookup to you. That is one command, and it is
the difference between a true statement and a satisfying one.

It also finds the boring, non-AI version of the same class of bug: an import
that works on your laptop only because something else dragged the package into
your install tree, and breaks the moment CI does a clean checkout.

## Install and run

Requires **Node 22 or newer** (developed on 26.7.0). There is nothing to
install — that is the point.

```sh
git clone https://github.com/Avi36005/ZeroDependency_Team_Kryptonite
cd ZeroDependency_Team_Kryptonite
make build          # verifies syntax and marks bin/depx.mjs executable
node bin/depx.mjs check /path/to/your/project
```

Or build the single-file version and run that anywhere:

```sh
make dist           # -> dist/depx.mjs, one file, no imports outside node:
node dist/depx.mjs check .
```

The rest of this README writes `depx` for brevity. Unless you link it onto your
`PATH` with `npm link`, run `node bin/depx.mjs` instead.

## Commands

| Command | What it reports |
|---|---|
| `depx check [path]` | everything (default) |
| `depx ghosts [path]` | only imports nothing in the project resolves |
| `depx phantom [path]` | only imports installed but never declared |
| `depx dead [path]` | only declared packages never imported |
| `depx replace [path]` | only packages the standard library already ships |
| `depx zero-dep [path]` | verify a repo against the Zero Dependency rule |
| `depx langs` | supported languages and their detection tier |

`[path]` may be a directory or a single file. A single file is judged against
its project's manifest, found by walking up from the file.

Options: `--lang <ids>`, `--json`, `--no-color`, `--quiet`, `--help`, `--version`.
Exit codes: `0` clean, `1` findings, `2` usage error.

## What the findings mean

| Finding | Meaning | Confidence |
|---|---|---|
| **ghost** | imported, and nothing in the project resolves it | high — see below |
| **broken** | a relative import pointing at no file on disk | high |
| **phantom** | imported and installed, but never declared | high |
| **undeclared** | imported, not declared, and we could not verify it exists | deliberately low |
| **dead** | declared but never imported | high — annotated when a build tool loads it |
| **replaceable** | declared, used, and the standard library ships an equivalent | high |

The **ghost / undeclared** split is the one design decision worth reading.

An undeclared import is only *provably* a ghost when we can see the whole
resolution universe. That is true in two situations: the manifest is
authoritative for the language (Go will not compile an import missing from
`go.mod`), or an install tree is present on disk to check against. With
neither, an undeclared import might simply be a real package nobody installed
here — so we report `undeclared`, not `ghost`.

The practical consequence: **run `depx` on a repo with its dependencies
installed** and you get strong claims. Run it on a bare checkout and it tells
you honestly that it cannot be sure.

### What is never a ghost

A false ghost is the worst bug this tool can have: it sends someone hunting
for a supply-chain attack that is not there, and a tool that cries wolf gets
uninstalled. So an import is excluded before it is ever judged when it is:

- **a module the repository defines itself** — `mod utils;` beside `src/utils.rs`,
  `import utils` beside `utils.py`, a directory module at `net/mod.rs`;
- **the project's own name** — Go's `module github.com/you/app` makes
  `github.com/you/app/internal/store` internal; a Rust binary under `src/bin/`
  importing its own crate (`use my_crate::api`) is the standard bin+lib
  layout; a package may import itself by name through its own `exports` map;
- **a subpath import or a bundler alias** — `#internal/x`, `@/components/y`,
  `~/utils/z`, `$lib/w`, none of which npm names can even begin with;
- **standard library** — including the ones that read like packages:
  Python's `__future__`, Ruby's `English`;
- **a relative path** — those are checked against the disk instead, and
  reported as `broken` if they miss. Ruby's `require_relative` is routed here
  rather than judged against the Gemfile.

An import is also never promoted from `undeclared` to `ghost` on the strength
of an install tree that turns out to be empty: a bare `.venv` directory with no
`site-packages` inside it is a directory, not evidence.

Each of these was a false positive found by running `depx` against real
repositories, and each has a regression test.

### Nested projects

A subdirectory with its own manifest is a different project, so `depx` does not
descend into it — judging its imports against your manifest would make every
finding noise. It says which ones it skipped, because a monorepo root
legitimately contains no source of its own and silence there reads as a broken
scan:

```
  scanned 0 files in 0 languages
  2 nested projects not descended into: client, server
  each has its own manifest - run depx inside it to check it
```

Cargo workspaces and npm workspaces behave the same way. Run `depx` once per
package; workspace linking is not resolved.

## Verifying the Zero Dependency rule

`depx zero-dep` checks both halves of the rule, not just the visible one.

```
$ depx zero-dep .

  Zero Dependency rule check

  PASS  package.json  no runtime dependencies

  empty manifest verified, no vendored source detected
```

An empty manifest is easy to verify and easy to fake. The rules close the
loophole in prose — copying a library into `src/` is "a dependency with extra
steps" — but nothing checks it, because the manifest still reads `{}`. So
`zero-dep` reads the code as well, and reports files that do not look
hand-written:

```
  REVIEW  source that does not read as hand-written
    src/bundle.js    :2
        carries a source map comment, which a build tool emits and a person does not write
        has a 904-character line, which means minified or bundled output
    src/vendored.js  :3
        carries a full third-party licence header, which is what copied library source looks like

  Signals, not proof. Vendored source must be disclosed in STDLIB.md;
  undisclosed, it scores against you.
```

These are **signals, not a verdict**. The tool cannot know who typed a line,
and it does not pretend to: it hands you a ranked list of files to open. The
false-accusation direction is the expensive one, so the markers are chosen to
be rare in hand-written code — and there are tests asserting that ordinary
source, and your own copyright line, stay silent.

It also catches the quieter failure: a repository with source but **no manifest
at all** cannot be verified at a glance, which is what the rule asks for.

```
  FAIL  requirements.txt  missing  34 Python files present

    add an empty requirements.txt so the empty manifest is verifiable on sight
```

## Language support

Ghost detection requires mapping an import name to a package name. How cleanly
that maps varies by language, so support is tiered and the tool never pretends
otherwise.

| Tier | Languages | Ghost detection |
|---|---|---|
| 1 | Go, JavaScript / TypeScript, Python | yes |
| 2 | Rust, Ruby | yes, after name normalisation |
| 3 | Java / Kotlin, C#, PHP, C / C++ | **no** — suppressed by design |

Tier 3 is a correctness decision, not a missing feature. In Java,
`import org.apache.commons.lang3.StringUtils` is satisfied by the Maven
artifact `org.apache.commons:commons-lang3` — the namespace and the coordinate
are different strings, related only by a mapping that lives on Maven Central.
Resolving that offline would need a shipped copy of the registry index. The
same holds for NuGet, and for Composer's PSR-4 map when `vendor/` is absent.
C and C++ have no dependency manifest at all.

For tier 3, `depx` reports file inventory and declared dependencies and stays
quiet about ghosts — and about `dead`, for the same reason: a coordinate never
literally matches an import namespace, so every declared dependency would be
reported unused. Emitting confident nonsense would be worse than saying
nothing.

## Honest limits

- **Static analysis only.** An import assembled at runtime
  (`require(process.env.PLUGIN)`) is invisible to us, by construction.
- **The JavaScript scanner is a lexer, not a parser.** It masks comments,
  strings, template literals and regex literals, then looks at what precedes
  each surviving string literal. It handles every import form we could think
  of and all of the decoys in `test/scanner.test.mjs`, but it does not build a
  syntax tree, so it cannot follow re-exports through aliasing.
- **Regex-versus-division** is resolved with the standard heuristic on the
  preceding token. This is the same heuristic real lexers use, and it is not
  perfect.
- **Python's import-to-distribution table is curated, not complete.** Thirty
  well-known aliases (`yaml`→`PyYAML`, `cv2`→`opencv-python`) are handled. An
  unusual alias will be reported as undeclared.
- **The TOML reader is a subset**: tables, dotted keys, strings, numbers,
  booleans, inline tables and multi-line arrays. That covers dependency
  manifests. Arrays of tables and datetimes are not implemented.
- **Monorepos**: `depx` analyses one project at a time, and names the nested
  projects it skipped so you know where to run next. Workspace linking is not
  resolved.
- **Nothing is verified against a registry.** `depx` is fully offline by
  design, so it can tell you an import resolves to nothing *here* and never
  that a package does not exist anywhere. The registry lookup on a ghost is
  yours to make.
- **`.gitignore` support is a subset** of git's matching rules — the common
  forms (`*`, `**`, `?`, anchoring, directory-only, negation), not the whole
  specification.
- **Symlinks are not followed.** A symlinked source directory is skipped
  rather than risk walking a cycle.
- **Files over 2 MB and files containing a NUL byte are skipped**, and counted
  in the `skipped` total so the number is never silently wrong.
- **Vendoring detection is heuristic** and reported as such. It finds copied
  code that still carries its provenance; it will not catch source that has
  been reformatted and stripped of headers. It is tuned to stay quiet on real
  code: across the seventeen repositories we tested it on, it flagged nothing
  hand-written. A single long line — an SVG path, a base64 URI, a row of
  Tailwind classes — is not treated as minification for that reason.
- **"Dead" does not mean "safe to delete."** A package can be loaded by a
  framework or named as a string in a build config, which is not an import.
  Those are annotated and sorted last rather than dropped, because "not
  imported" is still a fact worth showing.

## Zero dependencies

`package.json` carries an empty `dependencies` object and there is no
`node_modules` directory. [STDLIB.md](STDLIB.md) lists every package we would
normally have installed and the standard-library feature used in its place.
To check the claim rather than take it: `make proof`, or run the tool on
itself with `node bin/depx.mjs zero-dep .`.

### Reproducible build

`make dist` inlines the module graph into one file with `tools/bundle.mjs`, a
190-line bundler that is itself dependency-free. The output is byte-identical
across runs:

```
$ make verify
build 1: e401a03388887c213d087f7b00343dc406df906ff09d2dca9592fd05db6c4878
build 2: e401a03388887c213d087f7b00343dc406df906ff09d2dca9592fd05db6c4878
reproducible: byte-identical
bundle matches source tree
```

The second line matters as much as the first: `make verify` also diffs the
bundle's output against the source tree's, so a build that changed behaviour
would fail even if it hashed consistently.

## Development

```sh
make build     # syntax check + chmod
make test      # node --test, 159 tests across 42 suites
make dist      # single-file build
make verify    # build twice, compare hashes, diff behaviour
make snips     # regenerate snips/ - captured output per scenario
make proof     # regenerate deps-proof.txt
```

### Testing

159 tests across 42 suites, all stdlib (`node:test` + `node:assert/strict`).
The resolution, vendoring and CLI suites build throwaway projects under
`os.tmpdir()` and analyse them end to end — 70 of them by running
`bin/depx.mjs` as a child process and asserting on stdout and the exit code —
so the walker, the manifest readers, the report and the exit codes are all
exercised the way a judge or a CI job would exercise them.

Beyond the suite, `depx` was run against seventeen real repositories: every
public Zero Dependency 2026 submission we could find on GitHub, plus working
projects in Go, Rust, Python, TypeScript and JavaScript with real dependency
trees installed. It was also run against generated projects of 6,000 files
(0.65 s), deeply nested trees, CRLF and BOM sources, binary files with source
extensions, malformed manifests, symlink cycles, empty virtualenvs, Cargo and
npm workspaces, and adversarial scanner inputs for each language.

That campaign found twenty-one bugs — most of them false positives, several
of them claims the tool could not actually support. All are fixed, and every
one has a regression test named after the case that produced it.
